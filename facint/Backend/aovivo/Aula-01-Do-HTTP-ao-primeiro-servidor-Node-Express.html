🎤 **Fala do Professor:** "Toda aplicação web moderna tem duas grandes partes. O front-end é o que o usuário vê e com o que interage. O back-end roda no servidor e cuida de receber pedidos, aplicar as regras, acessar os dados e devolver respostas. Reparem no último item do front-end: o usuário pode inspecionar e alterar tudo o que roda no navegador. Por isso, qualquer regra importante, como 'só professor lança nota', precisa estar no back-end. Leiam o conceito-chave em voz alta: requisições, regras, persistência e segurança. Isso é praticamente o sumário das nossas quatro aulas."

🎤 **Fala do Professor:** "Essa divisão de papéis tem nome: modelo cliente-servidor. O cliente sempre inicia a conversa e o servidor fica de plantão. A mesma API acadêmica pode atender, ao mesmo tempo, o portal no navegador, o aplicativo no celular do professor e até a plataforma de pagamentos. Guardem a palavra stateless: por padrão o servidor não lembra de nada entre uma requisição e outra, como o caixa do supermercado, que pede o cartão a cada compra. Isso é ótimo para escalar, porque qualquer servidor de um grupo pode atender qualquer pedido. Mas é exatamente por isso que vamos precisar de tokens para saber quem está logado, assunto da nossa Aula 4."

🎤 **Fala do Professor:** "Vamos acompanhar o aplicativo do aluno pedindo a lista de cursos. Antes de falar com o back-end, o celular precisa descobrir o endereço IP do servidor: ele consulta o DNS, a agenda de contatos da internet. Depois abre uma conexão segura e envia a requisição. Em produção, quem recebe primeiro costuma ser um servidor web como o Nginx, que repassa o pedido para o nosso processo Node.js. A aplicação executa o código, consulta o banco e a resposta volta pelo mesmo caminho. Quando um sistema ficar lento no estágio de vocês, lembrem deste slide: o profissional experiente investiga etapa por etapa, rede, aplicação e banco, em vez de sair chutando."

🎤 **Fala do Professor:** "Uma confusão comum é achar que o back-end é um bloco único. Em produção, normalmente há um servidor web na entrada, como o Nginx, especialista em rede: aceitar milhares de conexões, negociar o HTTPS, comprimir respostas e entregar imagens. Atrás dele fica o servidor de aplicação, que no nosso caso é o próprio processo Node.js rodando o Express. No mundo PHP, esse papel é do PHP-FPM, como mostra o e-book. Uma diferença interessante: o Node já escuta uma porta sozinho, então em desenvolvimento nem precisamos do Nginx. Em produção, colocamos o Nginx na frente, cuidando do HTTPS na porta 443 e repassando para a porta 3000."

🎤 **Fala do Professor:** "Já sabemos quem conversa com quem. Agora vamos aprender a língua dessa conversa: o HTTP. A boa notícia é que o HTTP é texto, e dá para ler cada mensagem com os próprios olhos. Vamos abrir essa caixa."

🎤 **Fala do Professor:** "O HTTP, criado por Tim Berners-Lee no CERN, define como clientes e servidores trocam mensagens, e essas mensagens são texto. A requisição começa com uma linha com método, caminho e versão, segue com os cabeçalhos, uma linha em branco e, opcionalmente, um corpo. A resposta começa com a linha de status, como 200 OK. Lembrem das partes da URL: o host identifica o servidor, o caminho identifica o recurso e a query string carrega filtros, como ?curso=3. Minha dica prática: usem o curl com -v. Ele mostra tudo o que vai e volta, sem nenhuma interface gráfica escondendo detalhes. Daqui a pouco vamos fazer isso com o nosso próprio servidor."

🎤 **Fala do Professor:** "O método expressa a intenção: GET consulta, POST cria, PUT substitui, PATCH altera uma parte e DELETE remove. Dois conceitos que caem em entrevista de emprego: seguro é o método que não altera o servidor, como o GET; idempotente é aquele em que repetir dá o mesmo efeito. Apagar o aluno 42 uma vez ou dez vezes dá no mesmo. Já repetir um POST pode criar duas matrículas. Na direita, as classes de status: 4xx significa que quem pediu errou; 5xx significa que nós, do back-end, erramos. O código de status é como o garçom avisando o que aconteceu com o pedido, e é por ele que o aplicativo decide o que mostrar ao usuário."

🎤 **Fala do Professor:** "No HTTP puro, as mensagens trafegam em texto aberto. Qualquer equipamento no caminho poderia ler senhas e dados pessoais. O HTTPS resolve isso executando o HTTP sobre uma camada chamada TLS, que garante três propriedades: confidencialidade, integridade e autenticidade, esta última graças ao certificado digital. Hoje existem certificados gratuitos, como os do Let's Encrypt, então não há justificativa para publicar uma API sem HTTPS. Um detalhe importante: o Express em si não precisa saber de TLS; normalmente o Nginx ou a plataforma de hospedagem cuidam do certificado e repassam a requisição para o Node."

🎤 **Fala do Professor:** "Chegou a hora de colocar a mão no código. Vamos entender o que é o Node.js, por que ele atende muitas requisições com um único processo e, depois, escrever o nosso primeiro servidor."

🎤 **Fala do Professor:** "Quatro termos que muita gente mistura. A linguagem é a sintaxe; o runtime é o programa que executa o código, e o Node.js é exatamente isso: um runtime que roda JavaScript fora do navegador, usando o motor V8 do Chrome. Biblioteca é um código que você chama quando precisa; framework é quem define a estrutura e chama o seu código. A tabela vem do Quadro 7 do e-book: no PHP-FPM, cada requisição começa do zero; no Node, um único processo fica vivo atendendo muitas requisições. Nenhum modelo é melhor em absoluto; cada um exige cuidados diferentes. E guardem a frase do callout: ela volta com tudo na próxima aula."

🎤 **Fala do Professor:** "Como um único processo dá conta de tantas requisições? Pelo event loop, o laço de eventos. Quando o código precisa esperar o banco ou outra API, essa espera é delegada, e o processo segue atendendo outros pedidos. Quando o resultado chega, o callback entra numa fila e é executado. A analogia é o garçom eficiente: ele anota o pedido, entrega à cozinha e vai atender a próxima mesa, sem ficar parado olhando o fogão. Agora, se ele resolver descascar batatas no meio do salão, todas as mesas ficam esperando. É isso que acontece quando colocamos um cálculo pesado e síncrono dentro de uma rota. Vamos ver isso no código."

🎤 **Fala do Professor:** "Este é o menor back-end possível em Node.js, o mesmo do Código 8 do e-book. O createServer recebe uma função que é chamada a cada requisição, com dois objetos: req, a requisição, e res, a resposta. Acompanhem os números nos comentários: o código lê o método e o caminho, decide o que fazer, o que chamamos de roteamento, define o status e devolve uma representação em JSON. Se a rota não existir, devolve 404. Por menor que seja, esse código tem os elementos de qualquer back-end do mundo. Testei este exemplo: rodem com node e acessem com curl ou com o navegador. Agora imaginem cinquenta rotas com ifs desse jeito. É aí que entra o Express."

🎤 **Fala do Professor:** "Agora o mesmo servidor com Express, o framework web mais tradicional do Node. Reparem como o código fica declarativo: app.get com o caminho e a função. O Express cuida do roteamento, transforma o :id da URL em req.params.id, e o res.json serializa o objeto e já define o Content-Type. Acrescentamos uma segunda rota, a de um curso específico, que devolve 404 quando o curso não existe. Um detalhe que pega todo iniciante: tudo o que vem da URL chega como texto. Por isso convertemos com Number antes de comparar. Na próxima aula vamos abrir o Express por dentro e entender que tudo isso é construído com middlewares."

🎤 **Fala do Professor:** "Este experimento vale mais do que qualquer explicação. Rodem o arquivo, abram a rota /lenta numa aba e, logo em seguida, a rota /rapida em outra. A rota rápida vai demorar cinco segundos! Isso porque o while síncrono ocupa o único processo, e ninguém mais é atendido. É o garçom descascando batatas no salão. Agora façam o mesmo com /espera: ela também demora cinco segundos, mas a rota rápida responde na hora, porque a espera foi delegada. Na vida real, operações de banco e de rede já são assíncronas. O cuidado é com cálculo pesado: relatórios enormes, processamento de imagem. Esses vão para filas ou worker threads."

🎤 **Fala do Professor:** "Nosso servidor funciona. Agora vamos organizá-lo como um projeto profissional: dependências declaradas, versões travadas e configurações fora do código."

🎤 **Fala do Professor:** "Dependência é qualquer pacote externo de que o projeto precisa, e o npm é quem baixa, instala e registra essas dependências. Este é o package.json da nossa API, igual ao Código 9 do e-book. Repare nos scripts: npm run dev roda o servidor com --watch, que reinicia sozinho a cada alteração, e --env-file, que carrega o arquivo .env, recurso nativo do Node a partir da versão 20.6. O acento circunflexo do ^5.1.0 significa: aceite melhorias e correções, mas nunca uma versão que possa quebrar o meu código. Por isso o package-lock.json vai para o Git: ele garante que produção rode exatamente as versões testadas. Já a node_modules fica de fora, porque é reconstruída com npm ci."

🎤 **Fala do Professor:** "Uma aplicação real roda em vários ambientes: a máquina de vocês, o servidor de testes e a produção. Muda o endereço do banco, as credenciais e o nível de detalhe dos erros, mas o código precisa ser o mesmo. A solução, recomendada pela metodologia Twelve-Factor App, é separar configuração de código com variáveis de ambiente. No Node, elas ficam em process.env; o arquivo .env é carregado pelo --env-file. Reparem em duas boas práticas no config.js: ele é o único lugar que lê process.env, e ele falha logo na inicialização se faltar algo importante, em vez de quebrar no meio de uma requisição. E atenção ao caso real: apagar o commit não resolve. A credencial precisa ser revogada e trocada imediatamente."
