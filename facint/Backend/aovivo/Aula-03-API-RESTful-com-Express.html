🎤 **Fala do Professor:** "Olá, pessoal! Na última aula organizamos a cozinha: middlewares, Controller, Service e Repository. Hoje vamos cuidar da porta de comunicação da API com o mundo, ou seja, de como os clientes pedem as coisas e de como o back-end responde. A pergunta que guia a aula é simples: por que algumas APIs são intuitivas e outras obrigam o desenvolvedor a adivinhar nomes de rotas e formatos de resposta? Vamos aprender REST, URIs, verbos, códigos de status, validação com Zod e erros padronizados, tudo com Express."

🎤 **Fala do Professor:** "O roteiro: começamos entendendo por que precisamos de um contrato. Depois, os fundamentos do REST, desenho de URIs, o modelo de Richardson e os verbos. O bloco central é prático: status, rotas versionadas, validação com Zod e tratamento centralizado de erros no Express. Fechamos com paginação e documentação. No final, a nossa API vai responder de forma previsível em qualquer situação, de sucesso ou de erro."

🎤 **Fala do Professor:** "Estes são os seis objetivos. Os três primeiros são de projeto: entender REST de verdade, e não apenas uma API que devolve JSON, desenhar URIs e avaliar a maturidade de uma API. Os três últimos são de implementação no Express: status, validação e erros. Guardem esses verbos, porque eles também são um roteiro de revisão para a prova."

🎤 **Fala do Professor:** "Hoje, raramente um back-end serve apenas a um site. O mesmo sistema acadêmico atende o portal, o aplicativo, o financeiro, uma rotina de dados em Python e talvez a plataforma de uma empresa parceira, cada um numa linguagem diferente. Para que todos conversem de forma previsível, precisamos de um contrato claro: a API. Voltando ao restaurante: o cardápio é o contrato entre salão e cozinha. Uma API mal desenhada é como um cardápio sem preços nem descrições: todo mundo precisa perguntar ao garçom antes de pedir qualquer coisa. No nosso caso, o garçom é o desenvolvedor do back-end respondendo mensagens o dia inteiro."

🎤 **Fala do Professor:** "REST é um estilo arquitetural descrito por Roy Fielding em sua tese de 2000. Curiosidade: Fielding também foi um dos autores da especificação do HTTP. O conceito central é o recurso: qualquer informação que possa ser nomeada. Cada recurso tem uma URI, e o cliente nunca mexe no recurso em si: ele troca representações. Quando fazemos GET em /alunos/42, o servidor não manda o aluno, manda um documento JSON que representa o estado atual dele. É como a foto 3x4: ela não é você, é uma representação sua num momento. E o mesmo recurso pode ter várias representações, como JSON para o app e PDF para a secretaria."

🎤 **Fala do Professor:** "Fielding descreveu restrições que, quando respeitadas, produzem sistemas escaláveis; uma API que as segue é chamada de RESTful. Cliente-servidor: interface e armazenamento evoluem separadamente. Cache: as respostas dizem se podem ser reaproveitadas, e um detalhe legal é que o Express já gera o cabeçalho ETag sozinho, como vimos no curl da Aula 1. Interface uniforme: URIs e métodos sempre do mesmo jeito. Sistema em camadas: o cliente não sabe se há um Nginx no meio. A que mais cai em prova é a de ser sem estado: o servidor não guarda o contexto da conversa, então o cliente manda o token em toda requisição, e podemos ter dez instâncias do Node atrás de um balanceador."

🎤 **Fala do Professor:** "URIs bem desenhadas deixam a API intuitiva, e as regras são poucas: substantivos no plural para coleções, nunca verbos como getAlunos, porque a ação já é dita pelo método HTTP, e filtros, ordenação e paginação na query string. E quando a operação não é um simples CRUD, como cancelar uma matrícula? Tratamos como sub-recurso: POST em matriculas/7/cancelamento. Reparem também no /v1: uma API publicada é um contrato, e se um campo muda de nome, o app já instalado no celular do aluno quebra. No Express, versionar é trivial: cada versão é um Router montado num prefixo, e as duas convivem no mesmo servidor durante a transição."

🎤 **Fala do Professor:** "O modelo de Leonard Richardson mede o quanto uma API aproveita a web, em quatro níveis. No nível zero, o pântano do POX, existe um único endpoint que recebe tudo, com o nome da ação no corpo. No nível um, cada recurso tem sua URI, mas tudo é POST. No nível dois, usamos verbos e códigos de status com a semântica correta, e é aqui que está a maioria das APIs do mercado, inclusive a nossa. O nível três, HATEOAS, acrescenta links que dizem o que o cliente pode fazer em seguida; ele dá mais trabalho e nem sempre é aproveitado. O importante é decidir de forma consciente."

🎤 **Fala do Professor:** "Um endpoint é a combinação de um método com uma URI, e cada verbo tem uma semântica definida pela RFC 9110. A idempotência tem consequência real: se a internet cair durante um DELETE, o cliente pode repetir com segurança; repetir um POST pode criar uma matrícula duplicada. Na tabela da direita, a novidade desta aula: onde cada dado chega no Express. A rota identifica e vira req.params, a query refina listagens e vira req.query, o corpo leva os dados e vira req.body, e o cabeçalho leva credenciais, lido com req.get. Lembrem: req.params e req.query chegam sempre como texto."

🎤 **Fala do Professor:** "Agora vamos implementar o contrato. Status corretos, rotas versionadas, validação e erros padronizados. Tudo o que vem a seguir está no projeto de apoio e foi testado com requisições reais."

🎤 **Fala do Professor:** "O código de status é a primeira coisa que o cliente olha: é com base nele que o app mostra os dados, pede um novo login, aponta os erros ao lado dos campos ou avisa que o serviço está instável. Por isso, devolver 200 com uma mensagem de erro no corpo é uma das piores práticas que existem. Prestem atenção nas duplas: 401 é 'não sei quem você é', 403 é 'sei quem você é, mas você não pode'. 422 é dado mal formado, 409 é regra de negócio violada. O fluxo de baixo é um roteiro prático: se a requisição passar por todas as perguntas, é sucesso; se parar em alguma, vocês já sabem qual código devolver. E lembram da pergunta da Aula 1 sobre o banco fora do ar? A resposta é 503 com mensagem amigável."

🎤 **Fala do Professor:** "Vejam como o roteiro de status vira código. Cada rota declara o método, a URI, os middlewares e o controller. A rota de criação é a mais interessante: primeiro autenticar, que devolve 401 se não houver token; depois exigirPapel, que devolve 403 se o usuário não for administrador; depois validar, que devolve 422 se os dados forem inválidos; e só então o controller, que responde 201. Os dois primeiros vamos implementar na Aula 4. Lido da esquerda para a direita, o código conta exatamente a história do slide anterior. E o prefixo /api/v1 fica num único lugar, no app.js."

🎤 **Fala do Professor:** "No store, o service cria o aluno e respondemos 201 com o cabeçalho Location, que diz onde o recurso novo pode ser consultado. No show, se o aluno não existir, lançamos NaoEncontradoError; graças ao Express 5, esse throw dentro de uma função async vai direto para o tratador global, que responde 404. No index, a paginação: página mínima 1 e no máximo 100 itens por página, para ninguém pedir um milhão de registros de uma vez. À direita, o alunoResource é a nossa View: monta a resposta campo a campo. É o equivalente aos API Resources do Laravel, que o e-book apresenta. Só sai o que declaramos explicitamente."

🎤 **Fala do Professor:** "Toda informação que chega à API vem de fora e não é confiável. O Zod permite declarar o formato esperado num schema: nome com no mínimo três caracteres, e-mail tirando espaços e passando para minúsculas antes de validar, e cursoId convertido para número. O middleware validar recebe qualquer schema, executa e, se falhar, gera um ValidacaoError com a lista de campos, que o tratador transforma em 422. À direita, a resposta real que o projeto devolve, com o erro ao lado de cada campo, pronto para o front-end exibir. E um bônus: o req.dados só contém os campos declarados. Se alguém enviar papel ADMIN no corpo, esse campo é descartado."

🎤 **Fala do Professor:** "Uma distinção fundamental. Validação de entrada pergunta se os dados estão bem formados: o e-mail tem formato de e-mail, a nota está entre zero e dez. Regra de negócio pergunta se a operação é permitida agora: ainda há vagas, o e-mail já existe. A primeira fica no schema e devolve 422; a segunda fica no service e devolve 409. Por que separar? Se a regra de vagas ficasse no middleware de validação, ela não valeria para uma importação de planilha, que chama o service diretamente. E nunca confiem só na validação do front-end: qualquer um contorna com curl."

🎤 **Fala do Professor:** "Uma API profissional não espalha try/catch por todas as rotas. As camadas internas lançam erros com nomes de negócio, como VagasEsgotadasError, e esses erros não sabem nada de HTTP, preservando a independência do service. Um único tratador, registrado por último no app.js, tem a tabela que converte cada código de domínio em status HTTP e monta a resposta sempre no mesmo formato. Reparem no cuidado com erros 500: o detalhe técnico, a pilha de chamadas, vai para o log com o request_id, e o cliente recebe só uma mensagem genérica com o código para o suporte. Expor detalhes internos ajuda atacantes a mapear a aplicação."

🎤 **Fala do Professor:** "Este é o formato de erro da nossa API, definido pela RFC 9457. Os campos type, title, status e detail são padronizados: o type identifica o tipo de erro, o title é um resumo estável, o status repete o código e o detail explica o caso concreto. O campo codigo é uma extensão nossa, permitida pela RFC, e é muito útil: o aplicativo decide o que mostrar pelo código curto, sem depender do texto, que pode mudar ou ser traduzido. O resultado é uma API que sempre fala a mesma língua quando algo dá errado. Para quem consome, isso significa um único tratamento de erro no app inteiro."

🎤 **Fala do Professor:** "Imaginem um aluno abrindo um chamado dizendo só: deu erro na matrícula. A equipe precisa achar aquele registro no meio de milhares de linhas de log. O correlation ID resolve isso. O middleware requestId, que escrevemos na Aula 2, gera um valor único por requisição; o logger coloca esse valor em cada linha; e ele volta ao cliente no cabeçalho X-Request-Id e na mensagem dos erros 500. Quando o aluno manda o print com o ID, o suporte encontra tudo na hora. É como o número de protocolo da operadora de telefonia."

🎤 **Fala do Professor:** "Dois assuntos fecham o conteúdo. Listagens são as operações mais frequentes e, sem paginação, poderiam devolver milhares de registros. O formato com data e meta deixa o front-end tratar todas as listagens do mesmo jeito. Atenção à segurança: nome de coluna livre vindo da requisição no ORDER BY é injeção de SQL esperando para acontecer. À direita, a especificação OpenAPI descreve a API num arquivo legível por pessoas e máquinas; dele saem documentação interativa, clientes gerados e servidores simulados. No ecossistema Node, há bibliotecas que servem o Swagger UI a partir do openapi.yaml, e há abordagens code-first, que geram o contrato a partir dos schemas de validação."

🎤 **Fala do Professor:** "Vamos conectar a aula ao cotidiano. A API é o cardápio. Recurso e representação são a pessoa e a foto 3x4. Stateless é o caixa que pede o cartão a cada compra. 401 e 403 são a portaria: sem crachá é 401; com crachá, mas sem acesso à sala, é 403. 422 e 409 são o formulário preenchido errado e a resposta 'não há mais vagas'. E o correlation ID é o número de protocolo. A terceira coluna traz os mesmos conceitos na nossa API, porque a analogia ajuda a lembrar, mas o vocabulário técnico é o que vocês vão usar no trabalho."

🎤 **Fala do Professor:** "Vamos amarrar. REST: recursos identificados por URIs e manipulados por representações, sem estado. URIs no plural, sem verbos, versionadas. Nível 2 de Richardson como meta realista. Códigos de status como contrato. Validação na entrada com Zod, regras no service, resource na saída. E erros padronizados pela RFC 9457, tratados num só lugar e rastreáveis pelo correlation ID. A frase que resume tudo: uma boa API é previsível, e quem a consome nunca precisa adivinhar nada."
